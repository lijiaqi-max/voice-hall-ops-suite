# 项目接管分析与比赛冲刺路线

更新时间：2026-06-17

## 结论

当前项目已经从“比赛原型”推进到“生产候选”。管理台、后台、成员端、厅控端、财务报表、演示数据、发布产物和安全门禁都有可运行基础；真正上线仍被两类外部验收阻断：

1. VPS 上的 PostgreSQL、API、MinIO、Caddy HTTPS、备份恢复还没有实跑验收。
2. 微信 8.0.74 和映客 9.8.60 还没有在两台真机完成页面校准、覆盖安装、断网重连和 24 小时观察。

所以本项目下一阶段目标不应再继续堆功能，而是先完成“可控上线闭环”：VPS 实跑、真机校准、演示彩排、CI 发布门禁。功能扩展排在这些之后。

## 关键风险

### P0 上线阻断

- **VPS 未实跑**：本地没有 Docker Engine 生产验收记录，不能确认 PostgreSQL、MinIO、Caddy、备份恢复在目标机器可恢复。
- **真机校准未完成**：正式微信/映客能力必须保持关闭，直到包名、版本、页面节点、群名/语音房、断网恢复全部通过。
- **CI 需要远程确认**：GitHub Actions 已补 Android release lint、instrumentation 编译、权限边界和源码包白名单检查；仍需推送后确认远程 Actions 全绿。
- **未提交改动较多**：生产门禁改动还在工作区，必须分批提交并打 tag，否则比赛/上线回滚困难。

### P1 产品与体验风险

- 管理台没有明确的“上线向导”：新用户不知道下一步该建厅房、账号、规则、设备还是导账单。
- 设备校准是高风险流程，但 UI 现在只是一组按钮，缺少逐项检查清单和证据记录。
- 财务页面能算账，但还不像财务工作台：缺少异常分组、应收应付提醒、未分配流水入口和关账前检查面板。
- 成员端更像任务列表，缺少“今天该做什么、为什么优先、怎么汇报”的运营引导。

### P2 工程维护风险

- `OpsRepository` 和 Android `MainActivity` / Room 数据库文件都偏大，后续加功能会越来越难维护。
- MinIO 只在基础设施中存在，素材、附件、导入原文件还未真正对象存储化。
- 缺少可观测性：没有结构化 request id、业务指标、错误告警和部署后巡检脚本。
- 文档中 `COMPETITION_STATUS.md`、`TESTING.md` 有部分旧进度描述，需要与 2026-06-16 的生产候选状态合并。

## 产品改进空间

### 管理端

1. **上线向导**：把首次部署拆成 7 步：改密码、建厅房、建账号、建规则、注册设备、导账单、跑结算。
2. **校准工作台**：为微信/映客分别展示检查项、手机型号、App 版本、页面特征、测试结果、启用人和启用时间。
3. **财务驾驶舱**：增加总流水、净利润、待分配流水、主持预估费用、异常账单、待审核作业的统一红黄绿状态。
4. **关系运营看板**：按价值等级、最近互动、联系频率、禁止联系、成员完成率生成今日重点池。
5. **审计时间线**：客户、设备、结算、作业都应该有可读时间线，比赛时能清楚讲“谁在什么时候做了什么”。

### 成员端

1. **今日任务排序**：按优先级、截止时间、客户阶段和联系限制展示。
2. **提交模板**：把渠道、结果、下次提醒、备注做成结构化快捷项，减少成员乱填。
3. **离线同步解释**：把“待同步/冲突/已提交/审核通过”做成更清楚的状态说明。
4. **合规提醒**：在 AI 建议和人工备注处加入索礼、施压、虚假亲密、频繁催促的即时提示。

### 厅控端

1. **校准模式**：只读展示当前识别到的节点、页面类型、版本、群名/语音房，不写入业务数据。
2. **断线诊断**：显示最近 10 条事件、签名结果、服务端 ack、失败原因和重试次数。
3. **微信指令测试面板**：不用进正式群，也能在模拟群里跑完整指令表。
4. **麦时修正入口**：管理员可以对异常分段补原因、修正时长并同步云端。

### Figma / Product Design 后续交付

当前没有指定 Figma 文件，因此本轮不直接写入 Figma。建议下一步在 Figma 产出四类画板：

- **比赛 8 分钟故事板**：痛点、系统架构、主链路、财务价值、隐私边界。
- **管理台信息架构**：经营看板、厅控、账单、结算、作业、审计的页面关系。
- **上线向导高保真稿**：首次部署和真机校准的逐步 UI。
- **移动端状态组件**：成员端任务状态、厅控端同步/校准/异常状态。

## 后续开发路线

### 第 1 阶段：固化当前生产候选

- 分批提交当前未提交改动：设备注册与能力门禁、Android 厅控端、管理台设备页、文档和 Room schema。
- 更新 `COMPETITION_STATUS.md` 和 `TESTING.md`，删除过期进度。
- CI 已补 release lint、instrumentation 编译、权限边界和 `package-source.ps1` 白名单检查；下一步推送后确认远程 Actions 全绿，再补签名产物上传。
- 清理或确认 `services/api/data` 只作为本地运行目录，继续保持 gitignore。

### 第 2 阶段：VPS 真实上线验收

- 在 VPS 填写 `.env`，执行 `docker compose --env-file .env up -d --build`。
- 验证 `https://DOMAIN/api/health`、登录、创建厅房、生成设备令牌、禁用设备。
- 执行一次 `backup.sh` 和 `restore.sh`，恢复后核对账号、厅房、设备和审计日志。
- 导入一份脱敏真实官方账单，完成客户分层、作业生成、结算关闭和 XLSX 导出。

### 第 3 阶段：两台真机校准

- 微信手机：确认 `com.tencent.mm` 版本、群名、白名单指令、输入框、发送按钮、重复消息保护。
- 映客手机：确认 `com.meelive.ingkee` 版本、语音房页面、麦位节点、进入/离开/换位、10 秒防抖。
- 覆盖安装成员端和厅控端，确认权限清单和 Room 迁移。
- 录制真机成功路径和失败兜底视频。

### 第 4 阶段：比赛演示打磨

- 写 8 分钟逐字讲稿和 15 秒兜底切换话术。
- 建 Figma 故事板和管理台上线向导稿。
- 准备三套演示环境：真机 + VPS、本机模拟、录屏。
- 彩排至少 3 次，记录每次卡点和耗时。

### 第 5 阶段：赛后生产增强

- MinIO 接入账单原文件、素材、导出报表和附件。
- 增加 Prometheus/OpenTelemetry 或最小健康巡检脚本。
- 拆分后端 Repository、Android Activity 和 Room 巨型文件。
- 增加消息通知、话术版本管理、迁移审核界面和财务异常工作台。

## 我接下来接力开发的优先级

1. **先提交和固化当前改动**，否则后续所有分析都没有稳定基线。
2. **补 CI 发布门禁**，让每次提交自动证明 API、管理台、Android release、权限和签名都没坏。
3. **做上线向导与校准工作台**，这是从“能跑”到“别人能上线使用”的关键。
4. **跑 VPS 和真机验收**，这决定项目能不能称为正式上线。
5. **再做 Figma/比赛视觉材料**，把系统价值讲清楚，而不是只展示功能列表。
